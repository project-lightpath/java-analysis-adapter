## 0. Governing facts (verified against source)

- `ServiceLoaderDescriptorSource.MAX_ENUMERATED_ENTRIES = 1024` is shared by the
  whole `ScanState` and used at:
  - `ServiceLoaderDescriptorSource.serviceFileCandidates` `:88` (charge) and
    `:92` (retained candidate list via `retainSmallest`),
  - `ServiceLoaderDescriptorArchiveSource.enumerate` `:67` (charge per entry),
  - `ServiceLoaderDescriptorArchiveSource.retainDescriptor` `:117` (retained
    `ZipEntry` map).
  `SootUpInputLocationFactory:153` uses `MAX_DEPENDENCY_ENTRIES` (a different
  budget) and calls `retainSmallest`; `retainSmallest` therefore stays.
- Exhaustion emits `descriptor_enumeration_limit`, returns no candidates for the
  current source, and is scan-global: `ServiceLoaderDescriptorScanner.isUnique`
  `:80` requires `scan.diagnostics().isEmpty()` for DEFINITE.
- `retainSmallest`'s eviction branch is currently dead in production: both the
  enumeration charge and the retention cap are 1024, so entry 1025 fails
  `tryEnumerate` before retention can evict.
- Decompression is a separate shared 16 MiB byte budget
  (`archive_decompression_limit`) with a one-byte sentinel read. It is
  orthogonal and unchanged by this ticket. On decompression exhaustion
  `readDescriptors` `:131-139` skips the failing entry and keeps earlier
  descriptors from the same archive; this ticket does not change that (R5).
- Archive enumeration runs on `java.util.zip.ZipFile`, whose CEN is indexed
  before `tryEnumerate`. Our budget bounds production work, not the JDK CEN
  allocation (documented risk in `prod-integration-review.md`; FLPATH-5124).
- Policy (`POLICY-NUMBERS.md`): no count cap; 2 GiB raw directory-read budget;
  2 GiB spill quota; 16 MiB decompressed; 1 MiB per-entry; 128 MiB heap.
  Measured raw ~122 B/entry, spill ~136 B/entry.
- Local fixture measurements (JDK 27, `-Xmx1g`): 65,535-entry classic ZIP =
  6.4 MB / 0.14 s write / 0.05 s enumerate; 1,000,001-entry ZIP64 = 99 MB /
  1.5 s write / 0.19 s enumerate / 74 MB peak heap in `ZipFile`. Both are below
  the 512 MiB `MAX_ARCHIVE_BYTES` guard.

## 1. Spec-derived equivalence classes (every cell gets a test)

| Axis | Cells |
|---|---|
| Source kind | archive (`ZipFile`), directory (`DirectoryStream`) |
| Enumeration budget | under, exactly equal, one byte over, already exhausted before the next source |
| Charged bytes | ASCII name, name above the 122 B floor, multi-byte UTF-8 name, ZIP extra field / comment bytes, null extra+comment (plain jar) |
| Result semantics | complete => all descriptors; enumeration/retention exhausted => the abandoned archive or services listing contributes zero descriptors and a byte-denominated diagnostic (mid-archive collection rolled back); module-info is scanned independently for exploded directories; decompression exhaustion keeps earlier descriptors and is diagnosed (pre-existing, cell 17) |
| Rollback scope | per archive, per directory listing, module-info independence for exploded dirs |
| Scale | 1,025 (former cap), 65,535 classic ZIP, 1,000,001 ZIP64 |
| Interaction | decompression x enumeration (no cross-contamination, both directions), many small service entries x 16 MiB decompression, WAR x large enumeration, reader source-order starvation x budget |
| Determinism | descriptor order unchanged (`TreeMap` + reader sort); candidates stay in sorted path order (`TreeSet`), independent of `DirectoryStream` order |

Pairwise cells explicitly tested: directory x exact boundary; archive x
one-byte-over; archive x mid-archive rollback; UTF-8/null-extra x archive;
WAR x large enumeration; decompression x enumeration both directions; reader
ordering x shared budget; module-info x exhausted directory listing.

## 2. Implementation design (GREEN target)

### 2.1 Byte models and budgets

Three cumulative, scan-global budgets. Cumulative is deliberate and matches the
existing decompression budget; it is stated in the names and in javadoc and is
NOT a live/peak bound.

1. **Enumeration** — `MAX_ENUMERATION_BYTES = 2 GiB` (ratified rawMax).
   Per-entry charge: `max(MEASURED_RAW_BYTES_PER_ENTRY, estimated record bytes)`
   with `MEASURED_RAW_BYTES_PER_ENTRY = 122` (measured, POLICY-NUMBERS) and
   `ENUMERATION_RECORD_OVERHEAD_BYTES = 46` (ZIP CEN fixed header):
   - archive: `max(122, 46 + utf8(name) + extra.length + comment.length)`;
   - directory: `max(122, 46 + utf8(fileName))` — the entry's own name, not the
     absolute path, so cost is host-independent.
   **Honesty clause (kept in javadoc and in the PR):** below a ~76-byte name
   with no extra/comment the 122 floor binds, so the effective capacity is
   `2 GiB / 122 B ≈ 17.6M entries` — floor-dominated, i.e. a safety ceiling
   expressed in bytes, not a variable-cost model. Above the floor the record
   term governs and is tested (cell 10b).
2. **Retained result metadata** — `MAX_RETAINED_DESCRIPTOR_BYTES = 16 MiB`,
   charged `RETAINED_DESCRIPTOR_BYTES = 512` per retained descriptor candidate.
   512 B is a deliberately conservative model of one live `Descriptor` (two
   Strings, two `List`s, path String, 64-char fingerprint, object headers) plus
   its candidate `Path`/`ZipEntry` slot. Capacity: `16 MiB / 512 B = 32,768`
   candidate slots **per analysis** (32x the old 1,024 global cap; the ssc-demo
   baseline is 54). Names that are not binary class names are rejected before
   the charge (archive entries and directory candidates), and an explicitly
   observed single-file descriptor is charged too; a candidate that adds no
   descriptor restores its charge. This is the bound that removes the unbounded
   result/candidate map growth created by deleting both 1,024 caps. It is a
   *candidate-slot* bound, not a whole-heap bound: provider payload strings are
   still bounded only by the 16 MiB decompression budget (R11).
   Diagnostic: `descriptor_retention_limit` (new, byte-denominated, scan-global;
   blast radius stated in the commit message). Module-info `provides` also
   charge this budget (atomically: a partial module add is discarded), and a
   rolled-back source restores its retention charge.
3. **Decompression** — 16 MiB, unchanged in value, charge sites and semantics.

### 2.2 `ServiceLoaderDescriptorSource.java`

1. Delete `MAX_ENUMERATED_ENTRIES`; add the constants in §2.1, each with javadoc
   naming the policy file, the capacity formula, the floor dominance, and
   FLPATH-5124.
2. `serviceFileCandidates`:
   - `if (!state.tryEnumerate(path.toString(), directoryEntryBytes(path))) return Optional.empty();`
   - if the file is a service candidate:
     `if (!state.tryRetain(path.toString())) return Optional.empty();`
     then `candidates.add(path)` (no eviction, no silent drop).
3. `retainSmallest` unchanged (used only by `SootUpInputLocationFactory` now).
4. `ScanState`:
   - fields `maxEnumeratedBytes`, `enumeratedBytes`, `maxRetainedBytes`,
     `retainedBytes` (all `long`);
   - constructors `()` and `(long maxDecompressedBytes)` keep their current
     meaning; defaults for the other two budgets are the class constants.
     Tests and the sanctioned edit use explicit named factories to avoid
     positional mis-binding (NEW-5):
     `static ScanState withBudgets(long decompressed, long enumerated, long retained)`
     and `static ScanState withEnumerationBudget(long enumerated)`.
     Every factory validates all values positive;
   - package-private `enumeratedBytes()`, `remainingEnumerated()`,
     `retainedBytes()`, `remainingRetained()`;
   - `boolean tryEnumerate(String path, long bytes)`: if `bytes > remainingEnumerated()`
     emit `descriptor_enumeration_limit` with
     `"descriptor entry enumeration exceeds <maxEnumeratedBytes> bytes"`, return
     false; else `enumeratedBytes += bytes`, return true. Check before charge;
     no unreachable negative branch.
   - `boolean tryRetain(String path)`: if `RETAINED_DESCRIPTOR_BYTES > remainingRetained()`
     emit `descriptor_retention_limit` with
     `"retained descriptor metadata exceeds <maxRetainedBytes> bytes"`, return
     false; else `retainedBytes += 512`, return true.
   - delete `private int enumeratedEntries`.

### 2.3 `ServiceLoaderDescriptorArchiveSource.java`

5. `enumerate`: compute `entryBytes = centralDirectoryBytes(entry)`; charge
   `tryEnumerate(entryPath, entryBytes)`. For a root-level service descriptor,
   `retainDescriptor` becomes
   `boolean tryRetainDescriptor(map, entry, path, state)`: `putIfAbsent`
   (first-wins duplicate behavior, `TreeMap` order unchanged) after
   `state.tryRetain(path)` succeeds. If retention fails, `complete = false` and
   `break` (zero descriptors from this archive).
6. Add `static long centralDirectoryBytes(ZipEntry entry)` =
   `Math.max(122, 46L + utf8Length(entry.getName()) + length(entry.getExtra())
   + utf8Length(entry.getComment()))`, null-safe. Documented as an *estimated*
   CEN record size (legacy-encoded names are re-encoded as UTF-8; R8).
7. Add `static long directoryEntryBytes(Path path)` in the source class =
   `Math.max(122, 46L + utf8Length(path.getFileName().toString()))`; share one
   `utf8Length` helper.
8. **Budget seam for tests (intentional, package-private).**
   `ServiceLoaderDescriptorReader.scan(context, dependencies)` currently
   constructs `new ScanState()` inline (`:29`), so no factory-built state can
   reach the scan and cells 12/15 would be unwritable. Extract the body into
   `static Scan scan(AnalysisContext context,
   SootUpInputLocationFactory.DependencyResolution dependencies, ScanState state)`;
   the two-argument method delegates with `new ScanState()`. Add the matching
   `ServiceLoaderDescriptorScanner.scan(context, dependencies, state)` overload
   delegating to the reader. Source ordering, visited keys and authorization are
   unchanged; only the state becomes injectable. Cell 16 pins that the default
   overload still uses the adopted budgets.

No change to `readEntry`, decompression accounting, `readDescriptors`,
`readModule`, WAR diagnostics, visited keys, authorization, or reader ordering.

## 6. Residuals (stated in the PR)

- R1 **1 MiB per-entry cap**: absent in production; only the prototype's
  `spike.entryMax`. Read literally, no new cap is added; production's effective
  per-entry bound remains the shared 16 MiB decompressed budget. FLPATH-5124.
- R2 **2 GiB spill quota**: production has no spill; not applicable until the
  seekable parser lands (FLPATH-5124).
- R3 **128 MiB heap / flat memory**: not achievable on the `ZipFile` path; the
  JDK indexes the CEN before our budget runs (measured ~74 MB for 1M entries).
  `MAX_ARCHIVE_BYTES = 512 MiB` remains the only pre-enumeration guard.
- R4 **Diagnostic codes**: `descriptor_enumeration_limit` keeps its code with
  byte-denominated detail; `descriptor_retention_limit` is new and scan-global.
- R5 **Decompression partial results**: pre-existing per-entry skip semantics on
  decompression exhaustion are unchanged; removing the retained-entry cap means
  more service entries are read, so a decompression limit can now be reached on
  archives that previously stopped at 1,024 entries. Pinned by cell 17:
  one earlier descriptor survives, exactly two decompression diagnostics are
  emitted, and no enumeration/retention diagnostic is added.
- R6 **Cumulative budgets**: all three budgets are cumulative scan-global
  volumes, not live/peak bounds. A later source can be rolled back while live
  retained memory is small, and a large monorepo can exhaust the 32,768-descriptor
  retention capacity; both cases are diagnosed and downgrade certainty.
- R7 **Baseline fixture is external**: acceptance 1 depends on the sibling
  checkout; the contingency mirror is not equivalent evidence.
- R8 **Name encoding**: the archive charge re-encodes `ZipEntry` names as UTF-8,
  so it is an estimate of raw CEN bytes for legacy-encoded names (never below
  the 122 B floor).
- R9 **Java 17 parity** depends on CI or an installed JDK 17.
- R10 **ZipFile mutation/CRC/encrypted/multidisk** semantics are untouched and
  remain FLPATH-5124 scope.
- R11 **Provider payload amplification**: the retention budget charges retained
  descriptors (including module-info provides) but not provider-line payload.
  One descriptor file may still inflate to the shared 16 MiB decompression cap
  and produce many provider `String`s; this is pre-existing (the old count cap
  never bounded providers within a file) and remains a decompression-budget
  concern.
